ReputableChat rules, version 0.001

These rules define each record, its fields, and the rules for validating it.
This document is published in the genesis record, along with an identity
record for the developer. Whenever the rules change, a new record is added to
the chain, and every later record must conform to it.


1. RECORDS

A record is a payload and a signature over it.

The payload is a JSON object in canonical form: keys sorted, no whitespace,
UTF-8, and no floating-point numbers. A number that is not whole is written as
a decimal string, such as "0.5".

Record hash
  The SHA-256 hash of the record's contents. The contents are, at minimum, the
  record type, public key, ack, message and transaction timestamp; some record
  types add further fields. Each field is UTF-8 text with surrounding
  whitespace removed, and fields are separated by a newline. The text contains
  no control characters other than tab, newline and carriage return.

Record type (type)
  Three parts separated by colons. The first is always "reputablechat". The
  second is one of: attestation, identity, message, reaction or release. The
  third is the rules version the record conforms to. Records must conform to
  the newest rules; a record whose version does not match the current rules is
  ignored and considered invalid.

    Attestation  A public statement of how reliable other users are.
                 Example: reputablechat:attestation:v0.001
    Identity     A public declaration of identity, including a preferred
                 handle and public key.
                 Example: reputablechat:identity:v0.001
    Message      A message to be displayed on the network.
                 Example: reputablechat:message:v0.001
    Notice       An alert posted to the network, which may or may not be
                 displayed to users.
                 Example: reputablechat:notice:v0.001
    Reaction     A reaction to another message on the network, such as a like
                 or an emote.
                 Example: reputablechat:reaction:v0.001
    Release      A published version of the client.
                 Example: reputablechat:release:v0.001

Public key (pubkey)
  An Ed25519 public key written as base64url (32 bytes). An account is its
  key; nothing else identifies it.

  The signature is Ed25519 over the canonical bytes of the payload, made by
  the key in the payload's pubkey field, written as base64url (64 bytes).

Ack (ack)
  The record hashes of the most recent records the author had seen and chose
  to acknowledge: sorted, with no duplicates, at most 16. Empty in the genesis
  record and nowhere else. Every record it names must share this record's
  version, unless this is a release record. Following acks back from any
  record always leads to the genesis record.

Message (message)
  At most 16,000 bytes. It can carry a rules document such as this one, or a
  message to a chat room or forum.

Transaction timestamp (ts)
  The time the author says they signed, in whole seconds since
  1970-01-01 00:00 UTC. It is not verified, and the network largely ignores
  it.


2. IDENTITY DECLARATION RECORDS

An identity declaration requires one additional field, handle, and may also
carry avatar, bio and mpubkey.

Avatar (avatar)
  An image, named by the SHA-256 of its bytes in hex plus a file extension.
  Images are expected to be 128 x 128 with a common image extension. The
  network does not enforce either, but most servers will likely ignore images
  that do not conform.

Bio (bio)
  A short message about the user, 1 to 280 bytes.

Handle (handle)
  The network identifies each user by their public key, or master public key,
  which is neither pleasant to look at nor easy to read. So each user chooses a
  handle to be known by, 1 to 64 bytes. Handles are not unique: users and
  servers show the first few characters of the public key beside a handle, as
  a kind of last name. A server may also let users choose a more readable last
  name, and may enforce its own uniqueness if it wishes.

Master public key (mpubkey)
  Users will sometimes want to change their key for security, or need to
  recover their account after a key is compromised. So a master key should be
  created with the account and kept offline, to be used whenever the user
  changes keys. Changing keys, or telling the network a key has been
  compromised, requires posting a notice record. A master public key is an
  Ed25519 public key written as base64url (32 bytes).


3. ATTESTATION RECORDS

An attestation requires one additional field, scores, and may also carry
derived.

Scores (scores)
  A map from each rated user's public key to the author's opinion of them.
  Each value holds reputation and trust, both decimals from -1 to +1.
  Reputation is the author's opinion of the user's messages; trust is the
  author's opinion of the user's attestations. Trust is expected to be 0 or 1
  in most cases. A 0 marks a user who is honest but too trusting of bad
  actors: their messages are still seen, while messages from users only they
  recommend are ignored.

Derived (derived)
  The same format as scores, holding the reputation and trust the author has
  calculated for every user within N hops. The author calculates them with
  their own formulas, standard or custom. Any value is accepted, and has no
  effect on the record's validity, as long as it lies between -1 and +1 and
  each public key is a string of the correct length.


4. MESSAGE RECORDS

A message may carry one additional field, reply_to: the SHA-256 hash of an
existing record on the chain. It draws attention to that record, to reply to
it or comment on it.


5. RELEASE RECORDS

A release record marks the start of a change to the rules. It is the only
record whose ack may name records of an older version. Every record in its ack
must be of the same previous version, and every record that names the release
in its ack must be of the release's version.
