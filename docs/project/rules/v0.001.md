ReputableChat rules, version 0.001

These rules define each record, its fields, and the rules for validating it. This document is the body of the genesis record, which is the developer's identity declaration. Whenever the rules change, a new record is added to the chain, and every later record must conform to it. These rules distinguish between rules that are enforced and rules that are not. An unenforced rule is a suggestion: a record that ignores one is still accepted, but clients will likely ignore the nonconforming values.

1. RECORDS

A record is a payload and a signature over it.

Payload
  A JSON object in canonical form: keys sorted, no whitespace, UTF-8, and no floating-point numbers.

Signature
  Ed25519 over the canonical bytes of the payload, made by the key in the payload's pubkey field, written as base64url (64 bytes).

Record hash
  SHA-256 over the canonical payload, a newline, and the signature, written as 64 lowercase hex characters. It is the record's identity. Canonical JSON never contains a raw newline and base64url never does either, so no two different records share the input to this hash.

Text
  UTF-8 with surrounding whitespace removed. It contains no control characters other than tab, newline and carriage return. Limits are in bytes.

Decimal
  A number that is not whole, written as a string: an optional minus sign, a whole part of at most seven digits with no leading zeros, and optionally a point followed by one to eighteen digits, such as "0.5" or "-1".

2. FIELDS EVERY RECORD CARRIES

Record type (type)
  Three parts separated by colons. The first is always "reputablechat". The second is one of: attestation, identity, message, notice, reaction or release. The third is the rules version the record conforms to. Records must conform to the newest rules they acknowledge; a record whose version does not match those rules is invalid.

  Attestation: A public statement of how reliable other users are. Example: reputablechat:attestation:v0.001
  Identity: A public declaration of identity, including a preferred handle and public key. Example: reputablechat:identity:v0.001
  Message: A message to be displayed on the network. Example: reputablechat:message:v0.001
  Notice: An alert posted to the network, which may or may not be displayed to users. Example: reputablechat:notice:v0.001
  Reaction: A reaction to another record on the network, such as a like. Example: reputablechat:reaction:v0.001
  Release: A published version of the client. Example: reputablechat:release:v0.001

Public key (pubkey)
  The key that signed the record: an Ed25519 public key written as base64url (32 bytes). An account is its key; nothing else identifies it.

Ack (ack)
  The record hashes of the most recent records the author had seen and chose to acknowledge: sorted, with no duplicates, at most 16. Empty in the genesis record and nowhere else. Every record it names must share this record's version, unless this is a release record. Following acks back from any record always leads to the genesis record.

Body (body)
  Text, at most 16,000 bytes, and may be empty. It can carry a rules document such as this one, or a message to a chat room or forum.

Message timestamp (ts)
  The time the author says they signed, in whole seconds since 1970-01-01 00:00 UTC. It is not verified, and the network largely ignores it.

3. IDENTITY DECLARATION RECORDS

An identity declaration requires one additional field, handle, and may also carry avatar, bio and mpubkey.

Avatar (avatar)
  An image, named by the SHA-256 of its bytes in hex plus a file extension. Images are expected to be 128 x 128 with a common image extension. The network does not enforce either, but most servers will likely ignore images that do not conform.

Bio (bio)
  A short message about the user, 1 to 280 bytes.

Handle (handle)
  The network identifies each user by their public key, or master public key, which is neither pleasant to look at nor easy to read. So each user chooses a handle to be known by, 1 to 64 bytes. Handles are not unique: the first few characters of the public key are shown beside a handle, as a kind of last name.

Master public key (mpubkey)
  Users will sometimes want to change their key for security, or need to recover their account after a key is compromised. So a master key should be created with the account and kept offline, to be used whenever the user changes keys. Changing keys, or telling the network a key has been compromised, is done with a notice record. A master public key is an Ed25519 public key written as base64url (32 bytes).

4. ATTESTATION RECORDS

An attestation requires one additional field, scores, and may also carry derived.

Scores (scores)
  A map from each rated user's public key to the author's opinion of them. Each value holds reputation and trust, both decimals from -1 to +1. Reputation is the author's opinion of the user's messages; trust is the author's opinion of the user's attestations. Trust is expected to be 0 or 1 in most cases. A 0 marks a user who is honest but too trusting of bad actors: their own messages are still seen, but their attestations count for nothing, so nobody becomes visible on their recommendation alone.

Derived (derived)
  The same format as scores, holding the reputation and trust the author has calculated for every user within N hops. The author calculates them with their own formulas, standard or custom. Any value is accepted, and has no effect on the record's validity, as long as it lies between -1 and +1 and each public key is a string of the correct length.

5. MESSAGE RECORDS

A message's body holds its text, at least 1 byte. It may carry one additional field, reply_to: the record hash of an existing record on the chain. It draws attention to that record, to reply to it or comment on it.

6. REACTION RECORDS

A reaction requires two additional fields, target and reaction.

Target (target)
  The record hash of the record reacted to. Usually a message, but any record may be the target.

Reaction (reaction)
  Text, 1 to 64 bytes, such as an emoji or a word like "like". Each client decides which reactions it counts as positive, negative or neutral, and ignores any it does not recognize.

An account may react to the same target any number of times.

7. NOTICE RECORDS

A notice requires one additional field, kind: text, 1 to 64 bytes. The kinds below have a defined meaning; any other kind is accepted, and clients that do not recognize it will probably ignore it.

Alert
  A statement to the network, such as a planned outage, carried in the body. Clients decide whether to display it.

Key change
  Moves an account to a new key. Signed by the account's master key, so its pubkey is the master public key. It carries two more fields: account, the public key being replaced, and new_pubkey, the key that replaces it. Records signed by the new key belong to the account from then on. One not signed by the account's master key is accepted but has no effect.

Key compromised
  Tells the network an account's key can no longer be trusted. Signed by the account's master key or by the compromised key itself, and carries one more field: account, the compromised public key. Records that key signs after this notice are not the account's. One signed by any other key is accepted but has no effect.

8. RELEASE RECORDS

A release record marks the start of a change to the rules. It is the only record whose ack may name records of an older version. Every record in its ack must be of the same previous version, and every record that names the release in its ack must be of the release's version.
