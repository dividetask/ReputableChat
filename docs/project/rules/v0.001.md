ReputableChat rules, version 0.001

These rules define each record, its fields, and the rules for validating it. This document is the body of the genesis record, which is the developer's identity declaration. Whenever the rules change, a new record is added to the chain, and every later record must conform to it. These rules distinguish between rules that are enforced and rules that are not. An unenforced rule is a suggestion: a record that ignores one is still accepted, but clients will likely ignore the nonconforming values.

1. RECORDS

A record is a payload and a signature over it.

Payload
  A JSON object in canonical form: keys sorted, no whitespace, UTF-8, and floating-point numbers recorded as a string surrounded by double quotes.

Signature
  Ed25519 over the canonical bytes of the payload, made by the key in the payload's pubkey field, written as base64url (64 bytes).

Record hash
  SHA-256 over the canonical payload, a newline, and the signature, written as 64 lowercase hex characters. It is the record's identity. Canonical JSON and base64url never contain a raw newline, and base64url is written without padding.

Text
  UTF-8 with surrounding whitespace removed. It contains no control characters other than tab, newline and carriage return. Each field gives its own length limit, counted in bytes.

Decimal
  A number written as a string: an optional minus sign, a whole part with no leading zeros, and optionally a point followed by one to eighteen digits, the last of which is not zero, such as "0.5" or "-1". Zero is written "0", never "-0". Each number has exactly one spelling.

2. COMMON FIELDS

Unless otherwise stated each field is required. Some optional fields may be required by certain record types.

Record type (type)
  Three parts separated by colons. The first is always "reputablechat". The second is one of: attestation, identity, message, notice, reaction or release. The third is the rules version the record conforms to. Records must conform to the newest rules they acknowledge; a record whose version does not match those rules is invalid.

  Attestation: A public statement of how reliable other users are. Example: reputablechat:attestation:v0.001
  Identity: A public declaration of identity, including a preferred handle and public key. Example: reputablechat:identity:v0.001
  Message: A message to be displayed on the network. Example: reputablechat:message:v0.001
  Notice: An alert posted to the network, which may or may not be displayed to users. Example: reputablechat:notice:v0.001
  Reaction: A reaction to another record on the network, such as a like. Example: reputablechat:reaction:v0.001
  Release: A published version of the client. Example: reputablechat:release:v0.001

Account ID (id)
  The record hash of an account's first identity declaration. It is used to identify the account. This field is only ommitted in the first identity declaration.

Public key (pubkey)
  The key that signed the record: an Ed25519 public key written as base64url (32 bytes). This must match the public key or master public key of the most recent identity declaration from the account id. Records signed with a public key, or master public key that does not match the most current key is invalid and rejected by the network.

Ack (ack)
  The record hashes of the most recent records the author had seen and chose to acknowledge: sorted, with no duplicates, at most 16. Empty in the genesis record and nowhere else. Every record it names must share this record's version, unless this is a release record. Following acks back from any record always leads to the genesis record.

Body (body)
  Text, at most 16,000 bytes, and may be empty. It can carry a rules document such as this one, or a message to a chat room or forum.

Message timestamp (ts)
  The time the author says they signed, in whole seconds since 1970-01-01 00:00 UTC. It is not verified, and the network largely ignores it.

Target (target)
  Optional. The record hashes of a existing records on the chain that this record replies to, comments on or reacts to.

Note (note)
  Optional. A short message, 1 to 280 bytes.

Master public key (mpubkey)
  Optional. Users will sometimes want to change their key for security, or need to recover their account after a key is compromised. So a master key should be created with the identity declaration and kept offline, to be used whenever the user changes keys. The master public key can only be changed using a notice record with the current master public key.

3. IDENTITY DECLARATION RECORDS

An identity declaration requires one additional field, handle, and may also carry account, avatar, and bio.

Avatar (avatar)
  An image, named by the SHA-256 of its bytes in hex plus a file extension. Images are expected to be 128 x 128 with a common image extension. The network does not enforce either, but most servers will likely ignore images that do not conform.

Bio (note)
  A short message about the user, 1 to 280 bytes. Uses the note field.

Handle (handle)
  The network identifies each user by their account ID, which is neither pleasant to look at nor easy to read. So each user chooses a handle to be known by, 1 to 64 bytes. Handles are not unique: the first few characters of the account ID are shown beside a handle, as a kind of last name.

Changing keys, or telling the network a key has been compromised, is done with a notice record. A master public key is an Ed25519 public key written as base64url (32 bytes).

4. ATTESTATION RECORDS

An attestation requires one additional field, scores, and may also carry derived.

Scores (scores)
  A map from each rated user's account ID to the author's opinion of them. Each value holds reputation and trust, both decimals from -1 to +1. Reputation is the author's opinion of the user's messages; trust is the author's opinion of the user's attestations. Trust is expected to be 0 or 1 in most cases. A 0 marks a user who is honest but too trusting of bad actors: their own messages are still seen, but their attestations count for nothing, so nobody becomes visible on their recommendation alone.

Derived (derived)
  The same format as scores, holding the reputation and trust the author has calculated for every user within N hops. The author calculates them with their own formulas, standard or custom. Any value is accepted, and has no effect on the record's validity, as long as it lies between -1 and +1 and each key is an account ID.

5. MESSAGE RECORDS

A message's body holds its text, at least 1 byte. A message's target, if it has one, is the record it replies to or comments on.

6. REACTION RECORDS

A reaction requires target: the record reacted to. Usually a message, but any record may be the target.

The body holds the reaction, such as an emoji or a word like "like". Each client decides which reactions it counts as positive, negative or neutral, and ignores any it does not recognize.

An account may react to the same target any number of times.

7. NOTICE RECORDS

A notice requires one additional field, kind: text, 1 to 64 bytes. The kinds below have meaning relevant to the network. Any notice record with a different meaning are accepted by the network, but ignored by the network itself. It is expected servers will use their own kind definitions to indicate outages, or other information relevant to the server.

Key change
  Moves an account to a new key. Signed by the account's master key or current public key. The body is the new public key in base64url without padding. The note field, if it's value equals 'compromised', indicates the previous public key was compromised.

8. RELEASE RECORDS

A release record marks the start of a change to the rules. It is the only record whose ack may name records of an older version. Every record in its ack must be of the same previous version, and every record that names the release in its ack must be of the release's version.
